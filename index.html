Question 2: Why MapReduce struggles with iterative jobs

A machine-learning job makes 10 passes over the same 200 GB dataset. Explain where Hadoop MapReduce spends its time on each pass and how Spark avoids it.

Then prove it on your machine: build a DataFrame of 5 million rows with an expensive column, run 5 filter-and-count iterations without caching and again with cache(), and compare the timings.

Hint

MapReduce writes every job's output to HDFS and the next job reads it back. In Spark, look at what cache() keeps between actions.

Why it matters

MapReduce runs each pass as a separate job: read from HDFS, map, shuffle to disk, reduce, write back to HDFS with 3x replication. Ten passes means ten full disk round trips. Spark builds one DAG inside one application, keeps intermediate data in executor memory when you cache it, and reuses the same executors, so later passes skip the disk and the JVM start-up.

Question 9: Diagnose a slow stage from Spark UI numbers

A nightly join job that used to take 12 minutes now takes 50. The Summary Metrics for its slowest stage (200 tasks) show:

  • What is wrong?
  • Which Spark UI tabs and views confirm it, and what would you look for?
  • Give three fixes.

Hint

Compare the max with the median for each metric. One task is doing almost all the work.

Model answer

Data skew. One shuffle partition holds about 11 GB while the median is 62 MB, so one task runs for 47 minutes and spills while the other 199 finish in seconds.

Confirm it:

  • Stages tab, open the stage, sort the task table by Duration or Shuffle Read Size: one outlier task.
  • SQL / DataFrame tab: find which join or aggregation produced the stage, and its join keys.
  • Then count rows per key: df.groupBy("key").count().orderBy(F.desc("count")). Often the hot key is NULL or a default value such as "UNKNOWN".

Fixes:

  • Turn on AQE skew-join handling: spark.sql.adaptive.skewJoin.enabled=true.
  • Salt the hot key: add a random suffix on the big side and replicate the small side.
  • Broadcast the smaller table if it fits, which removes the shuffle entirely.
  • Filter or handle NULL keys separately if they are the hot key.

  • Usable: 10,240 - 300 = 9,940 MB
  • Unified: 9,940 x 0.6 = 5,964 MB
  • Protected storage: 5,964 x 0.5 = 2,982 MB (execution can borrow the rest and evict cached blocks above this line)
  • User memory: 9,940 x 0.4 = 3,976 MB, for your own data structures, UDF objects and Spark metadata
  • Overhead: max(384, 1,024) = 1,024 MB
  • Container: 10,240 + 1,024 = 11,264 MB (11 GB)

Python workers for UDFs run outside the JVM heap and use the overhead, or spark.executor.pyspark.memory if set. That is why heavy Python UDF jobs often die with "container killed for exceeding memory limits" even though the heap looks fine.

Question 7: Diagnose high GC time

The Executors tab shows GC time at 38% of task time, highlighted in red. List the likely causes and the fixes you would try, in order. Write the spark-submit options to switch to G1GC and log GC activity.

Hint

GC pressure means too many live objects on the JVM heap at once. Think about what puts them there.

What to say

Likely causes

  • Partitions too large, so each task holds a huge working set.
  • Too many deserialized objects cached in memory.
  • Large collect() or broadcast results sitting on the heap.
  • RDD code that builds many small Python-to-JVM objects or large per-key collections (groupByKey).

Fixes, roughly in order

  • More, smaller partitions (raise spark.sql.shuffle.partitions or repartition).
  • Unpersist what you don't need; cache only what is reused; use DISK_ONLY or MEMORY_AND_DISK for big caches.
  • Replace RDD and UDF code with DataFrame built-ins, which use compact Tungsten binary rows instead of Java objects.
  • Use G1GC (default on Java 9+) and tune it, or give executors more memory with fewer cores so each task gets more heap.

[Meta 2025 Assessment]Medium

Question 2: repartition versus coalesce

Start from 8 partitions of 1,000 rows. Reduce to 3 partitions with coalesce(3) and with repartition(3). For each, count rows per partition with spark_partition_id() and look at the plan. Which would you use before writing a single output file from a large job, and why?

Hint

coalesce merges neighbouring partitions without a shuffle; repartition shuffles rows round-robin.

Why it matters

coalesce(1) before a write avoids a shuffle, but it can also pull the upstream work into one task, so the whole job runs on one core. For a large job, repartition(1) keeps the heavy work parallel and only the final write is single-threaded. For small outputs, coalesce is fine.

Question 3: Size partitions for a real cluster

A job reads 600 GB of Parquet and its aggregation shuffles 150 GB. The cluster has 40 executors with 5 cores each. Answer:

  • How many input partitions does Spark create with the default spark.sql.files.maxPartitionBytes, and how many waves of tasks is that?
  • What spark.sql.shuffle.partitions would you set for the aggregation if you want about 200 MB per shuffle partition?

Hint

Default max partition bytes is 128 MB. A wave is one round of tasks across all cores.

Model answer

  • Input partitions: 600 x 1024 / 128 = 4,800.
  • Cores: 40 x 5 = 200, so 4,800 / 200 = 24 waves.
  • Shuffle partitions: 150 x 1024 / 200 = 768. Round to a multiple of the core count: 800 (4 full waves).

Rules of thumb: aim for 100-200 MB per partition, and make the count a multiple of the total cores so the last wave is not mostly idle. With AQE on, you can set a generous number and let Spark coalesce towards advisoryPartitionSizeInBytes.

Question 7: Tune automatic broadcasting

A 25 MB dimension table is joined to a 2 TB fact table. Answer:

  • Will Spark broadcast it with default settings? Why or why not?
  • How do you make it broadcast automatically?
  • Why not just set the threshold to 2 GB?
  • How can AQE change the join strategy at runtime even when the planner chose sort-merge?

Hint

The default spark.sql.autoBroadcastJoinThreshold is 10 MB, and it is compared to Spark's size estimate, not to the file size on disk.

What to say

  • No. 25 MB is above the 10 MB default. Note that a Parquet file expands in memory, so the estimate can be several times its size on disk.
  • Raise the threshold (for example to 50 MB), or use the broadcast() hint on that join only.
  • A huge broadcast is collected on the driver and copied to every executor. It can run the driver out of memory, stall the network, and there is a hard limit of 8 GB per broadcast table. A sort-merge join is safer at that size.

Question 4: Pick the right trigger

Five files are waiting in the input folder and the source has maxFilesPerTrigger=2. For each trigger below, say how many micro-batches run, how many files each processes, and whether the query stops by itself:

  • default (no trigger)
  • processingTime="30 seconds"
  • availableNow=True
  • once=True

Hint

availableNow respects rate limits; once ignores them. Continuous processing supports only map-like queries on a few sources.

What to say

  • Default: 3 batches (2, 2, 1 files), each starting as soon as the previous one finishes. Keeps running, waiting for new files.
  • processingTime 30 s: 3 batches (2, 2, 1), at most one every 30 seconds. Keeps running.
  • availableNow: 3 batches (2, 2, 1), then stops. Best for scheduled, batch-style runs of a streaming pipeline.
  • once: 1 batch with all 5 files (ignores maxFilesPerTrigger), then stops. Deprecated in favour of availableNow, which also avoids one giant batch.

Question 5: Look inside a checkpoint

Run the console query from the first question with checkpointLocation=/tmp/chk/orders_console, let it process two files, then stop it. List the checkpoint folder and explain each item.

Then predict what happens when you restart the query after dropping a third file, and what happens if you delete the checkpoint first.

Hint

The checkpoint holds the write-ahead log of planned offsets, the record of committed batches, and the file source's own log of seen files.

What to say

  • metadata: the query ID, which stays the same across restarts.
  • offsets/N: written before batch N runs: which input that batch will read (here, file-log index) plus the watermark and configs.
  • commits/N: written after batch N finishes successfully.
  • sources/0/: the file source's log of every file it has already processed.
  • state/: appears only for stateful queries (aggregations, deduplication, stream-stream joins).

Restart with the same checkpoint: batch 2 processes only the third file. Batch IDs continue. Delete the checkpoint: the query starts from scratch and reprocesses all three files, duplicating output in a non-idempotent sink.

Small changes such as adding a filter are usually fine across restarts; changing grouping keys or aggregations breaks the stored state and needs a new checkpoint.
